# Participant Application

The participant application presents the pairwise face-comparison task generated by the researcher dashboard.

It is deliberately lightweight and implemented with:

```text
HTML
CSS
JavaScript
```

The participant application is separate from the scientific analysis code.

It does not select stimuli, generate experimental pairs, fit Bradley–Terry models, process facial landmarks, or reconstruct faces.

Its role is only to present the experiment and collect participant responses.

## Generated experiment

The researcher application generates:

```text
apps/participant/experiment.json
apps/participant/stimuli/
```

`experiment.json` describes the current experimental trials.

Each trial contains information such as:

```json
{
  "pair_id": "PAIR_00001",
  "pair_order": 1,
  "model_left": "BM-001",
  "model_right": "WM-012",
  "image_left": "stimuli/BM-001.jpg",
  "image_right": "stimuli/WM-012.jpg"
}
```

The `stimuli/` directory contains only the images required for the active experiment.

## Important: generated data are not versioned

The following files are generated locally and must not be committed to GitHub:

```text
apps/participant/experiment.json
apps/participant/stimuli/
```

In particular, Chicago Face Database images must not be distributed through this repository.

The repository should contain only the participant application code:

```text
apps/participant/
├── index.html
├── script.js
├── style.css
└── README.md
```

## Participant workflow

The current task flow is:

```text
Start screen
    ↓
Pair 1
    ↓
left / right choice
    ↓
Pair 2
    ↓
...
    ↓
Final screen
```

For each trial, the participant sees two faces and selects one of them.

The task can optionally enforce a response deadline if one was configured by the researcher.

## Response schema

The participant task records one row-like response object per trial.

The core response schema is:

```text
participant_id
trial_index
pair_id
model_left
model_right
selected_model
response_time_ms
```

Example:

```json
{
  "participant_id": "P001",
  "trial_index": 12,
  "pair_id": "PAIR_00012",
  "model_left": "BM-001",
  "model_right": "WM-012",
  "selected_model": "BM-001",
  "response_time_ms": 1342
}
```

These fields are designed to feed directly into the participant-specific Bradley–Terry analysis.

## Participant identifiers

During local development, the participant identifier can be supplied through the URL:

```text
?participant_id=TEST001
```

The application can also read a Prolific-style identifier:

```text
?PROLIFIC_PID=...
```

The participant-ID handling will ultimately be integrated with the deployment environment and JATOS.

## Local testing

The participant task should be served through a local HTTP server rather than opening `index.html` directly, because the application loads `experiment.json` with `fetch()`.

From the repository root:

```bash
python -m http.server 8000 -d apps/participant
```

Then open:

```text
http://localhost:8000/?participant_id=TEST001
```

A participant experiment must first have been generated from the researcher application.

## Current local-development output

During local development, responses can be inspected or exported locally.

This behavior is temporary.

The intended production data flow is:

```text
Participant task
      ↓
JATOS
      ↓
participant response data
      ↓
Researcher dashboard
      ↓
Bradley–Terry analysis
```

## JATOS integration

The participant application is intended to be deployed through JATOS.

The next integration stage will replace local response export with JATOS result submission.

JATOS will be responsible for storing the participant response data generated by the task.

The researcher application will later provide an import stage for these collected responses.

## Separation of responsibilities

```text
Researcher application
    experiment configuration
    stimulus selection
    pair generation
    analysis
    reconstruction

Participant application
    trial presentation
    participant input
    response timing
    response submission

src/face_reconstruction
    reusable scientific algorithms
```

Keeping these components separate prevents scientific processing logic from being duplicated inside the participant interface.
